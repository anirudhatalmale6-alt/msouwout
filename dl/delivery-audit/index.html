MyPlopPlop Delivery: Audit Against Your 17 Points

15 Oct 2026. Every line comes from reading the LIVE code (backend and website), not from memory. Works exists end to end · Partial exists with a gap · Missing / bug · Fixed today already live.

Summary

Not ready for public launch. The ordering and payment basics exist, and the server verifies payments itself. But:

  • Drivers are never actually credited for a dispatched delivery.
  • The delivery code does not prove delivery.
  • Nothing undoes money when an order is cancelled.
  • Pickup verification and live tracking do not exist.

I also found and closed 9 live security holes today, including a 20 HTG payment able to complete a 50,000 HTG top-up. Nobody had used any of them; I checked the records.

Fixed and live today

  • FixedDelivery split: drivers were paid 75%, not 80%, on dispatched deliveries. Now 80/20, calculated on the server.
  • FixedAny merchant could make himself the "driver" on any order, read the customer's phone and address, mark it delivered and be paid.
  • FixedAny logged-in user could read any delivery: the customer's name, phone, address, GPS and delivery code.
  • FixedAn old referral bonus paid wallet money when an order was PLACED, before payment. Unpaid orders created spendable money.
  • FixedA public page listed drivers' names, phones, licence numbers, ID-photo paths and exact GPS.
  • FixedA public page returned everybody's prepaid electricity tokens.
  • FixedA MonCash check could complete a big wallet top-up with a small payment, or with someone else's payment.
  • FixedAnyone could pay for someone else's ride from their wallet, crediting the driver again on every tap.
  • FixedA delivery's driver status was readable by anyone.

1. Customer ordering

  • WorksCart with several shops, prices and quantities; delivery fee and service fee shown separately before paying.
  • WorksAn order is marked paid ONLY after the server checks with SolutionIP itself. Returning from MonCash alone never marks it paid.
  • PartialSearch: shops by name only. Products are never matched.
  • PartialAddress: GPS is required. If GPS fails there is no way to place the pin by hand, and GPS accuracy is not checked.
  • BugThe delivery distance starts from central Port-au-Prince, not from the shop, so the fee can be wrong.
  • BugSeveral shops in one basket: one payment, but only the FIRST shop's order is ever marked paid.
  • MissingIf the customer closes the browser after paying, nothing confirms the payment later (no webhook, no server check).
  • BugThe tracking page always says "Ride Not Found", and deliveries never appear in the customer's history: the page and server disagree on a field name.

2. Merchant order management

  • WorksSees own orders, products, quantities, the assigned driver. Cannot change an order's amount after it is placed.
  • MissingNo new-order alert: merchants only see orders when they reload the page.
  • BugUNPAID orders look like real ones. The merchant can prepare one and mark it Ready, and that sends a driver.
  • BugNo status rules: a merchant can mark a delivery order "delivered" with no driver and no code, and is credited.
  • BugThe merchant's screen shows the customer's delivery code.
  • MissingRejecting a paid MonCash order: no refund record, nothing for an admin to act on, stock not restored.
  • PartialSeller fee and expected settlement: built with the new pricing (not active). Dashboard "revenue" also counts unpaid orders.

3. Driver registration

  • WorksName, phone, vehicle, plate, licence number. Admin approves or rejects. Only approved drivers receive requests.
  • MissingThe form sends no ID, licence or vehicle photos, no profile photo, and no MonCash/NatCash payout number.
  • MissingNo "suspend" button. A driver rejected mid-delivery can still finish and be paid.
  • PartialUploaded documents are kept on the server's temporary disk, which can be wiped at each update.

4. Availability and assignment

  • WorksOnline/offline; nearest approved online driver within 15 km; 30 seconds to answer, then the next driver.
  • BugAccepting is not protected: two drivers can accept the same delivery at the same moment.
  • BugIf the driver cancels after accepting, the order is stuck forever and never offered again.
  • BugNo driver available: it retries forever, re-offering to drivers who already declined. No alert to the customer or admin.
  • PartialDriver positions are never refreshed after going online, so "nearest" can be stale. Customer and merchant see the driver only after reloading.

5 + 6. Delivery pricing and the 80/20

  • Fixed80% driver / 20% HaitiBiznis, worked out on the server and stored separately from product sales.
  • WorksThe driver sees the amount before accepting. The customer's fee does not change after payment.
  • BugAt dispatch the driver's fare is recalculated from the distance, so it can differ from 80% of what the customer actually paid.
  • BugOne ride route lets the person creating the ride set the distance, and so the price.

7. Pickup verification

  • MissingNo merchant confirmation, no pickup code or QR, no pickup location. "Arrived at store" is recorded as the pickup time.

8. Delivery tracking

  • MissingNo live driver location is sent; the map is a placeholder and the arrival time is fixed text. It reopens after a reload, but there is nothing to show.

9. Delivery confirmation code

  • PartialA 4-digit code exists and the server checks it when the driver finishes from the delivery app.
  • BugThe CUSTOMER is never shown the code. The merchant is, and drivers can still read it in their own offer screens.
  • BugAnother route marks an order delivered with no code at all. Unlimited guesses are possible. There is no admin exception process.

10. Driver payments

  • CriticalA driver who completes a dispatched delivery is NEVER credited to their wallet: only a record is written. They can never withdraw.
  • MissingNo pending / available / paid split for drivers. MonCash/NatCash payout fees are not recorded anywhere. Payouts are manual.

11. Merchant settlements

  • WorksA merchant is credited only when an order is delivered AND paid, into a pending balance.
  • BugNothing moves pending money to available (no schedule, no admin button), so merchants can never withdraw.
  • BugDelivered first and paid later: never credited. Two simultaneous "delivered" taps, or two payout requests, can both succeed.

12. Cancellations, refunds, disputes

  • MissingNo refund record (amount, reason, reference, status, approval) and no admin refund screen.
  • BugCancelling never undoes the merchant credit, driver earning, Ajan commission or stock.
  • BugA cancelled order's delivery keeps running. If delivered, it pays everyone. A customer can even cancel AFTER delivery.
  • MissingProduct unavailable, customer unreachable, wrong or damaged package: no flow. The "report a problem" button sends to the wrong service.

13. Notifications

  • PartialWeb push only, with passenger-ride wording, for: driver assigned, at the store, picked up, delivered, driver cancelled.
  • MissingNothing for: order placed, payment confirmed, merchant accepted, preparing, approaching, merchant/customer cancel, refund. No SMS or WhatsApp for orders.

14. Administrator dashboard

  • PartialCounts and lists of rides and orders; a read-only orders page.
  • MissingOrders waiting for a driver, driver map, delayed or failed deliveries, complaints, driver earnings, net revenue, refunds, payout release.
  • BugAdmin actions that move money are not recorded with who did them. The console code can be passed in a link, and the original setup code never stops working.

15. Security and fraud

  • FixedThe 9 holes above.
  • BugUnpaid orders can be dispatched. Status changes have no rules. The delivery code is visible to drivers. Live-update channels need no login, and driver locations can be faked.
  • BugA driver can create a ride as a customer and accept it himself, generating earnings with no money paid. A merchant can lift his own suspension.
  • MissingAn audit log of financial changes (only driver approvals and store edits are logged).

16 + 17. Testing and report

The 10 end-to-end scenarios cannot pass today: drivers are never credited and tracking shows "Ride Not Found". They should be run after the must-fix list below. For the final real-money test, one controlled 20 HTG order is enough, as with MsouWout.

Before public launch (your 5 mandatory areas)

  • 1. Server-confirmed payment: no merchant preparation and no dispatch until the server has confirmed payment; a server-side check for customers who close the browser; one payment confirms every shop in the basket; the server's total is charged (already built, waiting).
  • 2. Reliable assignment: one driver per delivery (protected accept); re-offer when a driver cancels; no-driver timeout with an alert and an admin list; refresh driver positions.
  • 3. Pickup and delivery proof:
    • The code is shown ONLY to the customer (order page + notification) and is hidden from drivers and merchants.
    • Every "delivered" path requires it, with an attempt limit.
    • A pickup code, or the merchant's confirmation, at the store.
    • An admin exception with a reason, logged.
  • 4. Accurate 80/20 earnings: credit the driver on a genuine completion (pending → available); the driver's 80% always taken from the stored delivery fee; completion counted once.
  • 5. Cancellations and refunds:
    • Refund records with admin approval.
    • Cancelling undoes the merchant credit, driver earning, Ajan commission and stock, and stops the ride.
    • Status rules (no cancel after delivery, no "delivered" by the merchant on a delivery order).

After launch, progressively: live GPS tracking, full notifications, the admin operations dashboard, complaints, driver documents and photos, and the payout engine (it needs SolutionIP's answers).
